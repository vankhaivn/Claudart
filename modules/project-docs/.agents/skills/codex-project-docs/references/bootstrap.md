# Init and adopt

Use this reference only when establishing project docs or taking over an existing project. Read [ownership](ownership.md) before selecting canonical destinations.

## Init: learn what matters

Inspect the repository, any existing brief, and the user's stated goal first. Interview only for material gaps: who uses the product, what outcome and behavior are agreed, important domain terms and constraints, delivery context, and what remains undecided. Ask the highest-value question next rather than walking a fixed questionnaire. A short idea can be captured provisionally with explicit assumptions and open questions; do not imply an unapproved choice is settled.

Keep raw interview notes or synthesis in the active work surface while decisions are forming. Once a claim has the needed approval or evidence, distill it into the appropriate current owner and route to it. Raw discovery is input, not permanent superior authority. Do not make an interview transcript, numbered document pack, or empty placeholder files the default output. If the user asks only to clarify the idea, deliver that understanding without starting implementation or inventing a permanent docs tree.

## Adopt: recognize existing authority

Inventory only the relevant repo paths and existing docs router, source/schema/generated references, knowledge routes, task/spec records, and accessible team-owned sources. Record which topics already have a useful owner, which are duplicated, and which are genuinely missing or contradictory. Ask the person adopting the project about their responsibility and goals; do not require them to redecide company-owned product facts or speak as the original founder.

For each affected topic, identify its current owner, evidence or gap, and smallest action (keep, update, link, or consolidate) in the existing work output. Follow the ownership reference before proposing a move. Healthy docs and knowledge may need no changes; do not add a manifest, force a new page, or rewrite the repository to complete adoption.

Preserve custom, untracked, original-input, and team-owned documents. Do not overwrite an external source or migrate a repo-specific structure just to match a template. For conflicting claims, use the ownership procedure and seek the actual decision authority when evidence cannot resolve them. Report a concrete gap rather than creating a speculative page. Installation approval alone does not authorize authoring or moving live documentation; an adoption request authorizes only its scoped changes.

## Choose the smallest usable shape

Write only current material that has a real reader and owner. A single overview may suffice. Split product/domain, architecture/reference, setup/operations, or capability/release information only when different content, readers, or maintenance needs justify it. Use the repository's router convention or, when appropriate, `docs/README.md` to direct readers to owners and known gaps. Keep links to external authority as links; do not republish its content as if this module owned it.

For missing or unsuitable pages, use the [template selection guide](templates.md) and adapt only the needed output templates. It supplies concrete product, behavior, architecture, development, and operations responsibilities without requiring a file for each. At idea stage, a router and product brief can suffice; do not fabricate implementation or release procedures. For an adopted project, map these responsibilities to valid existing owners before creating anything. Read a filled example only when it helps resolve the output shape.

Finish by identifying what was established, what was adopted unchanged, assumptions requiring a decision, and the evidence for claims about current behavior. Avoid describing plans, tasks, or unshipped work as current capability.
